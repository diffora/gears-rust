## Contract profile and ownership

**Proposed profile identifier: `subscriptions-rating/1`.** This names the semantic package in this proposal; it is not the existing Rating SDK V1. A deployment enables a charge-kind/model/policy combination only when Subscriptions, Rating and Billing advertise the same adopted profile and limits. Lot-aware mandatory fields and changed binding semantics cannot silently extend an already shipped V1 contract: use an explicitly selected profile on an unshipped interface or a new major wire/SDK contract where compatibility requires it. No migration adapter is required by this proposal.

| Owner | Authoritative decisions | Consumed evidence |
| --- | --- | --- |
| Subscriptions | Economic occurrence, immutable billing group, actual applied service boundaries, full quantity-lot timeline, accepted terms, commercial seal, historical attribution | Orders/Pricing acceptance and applied operation evidence; resource lifecycle/inventory evidence |
| Pricing | Approved money/model/descriptors, immutable commercial acceptance and supported continuation rules | Authorized commercial query and accepted pins; no Rating-owned tariff selection |
| Rating | Exact valuation, calculation generation/snapshot, child enumeration and verified usage completeness, full result revisions | Exact fact, accepted inputs, attribution/inventory/usage proofs; Billing state is not an input prerequisite |
| Billing | Invoice-line equivalence, full financial target, benefit/advance allocation, rounding, draft/posting fences and financial corrections | Commercial seal plus compatible complete Rating results; authoritative prior financial outcomes |

The profile supports only explicitly enabled recurring, usage and qualifying one-time combinations. Contract overrides, FX, coupons, commitments/reservations, migration/import, backdating, decreases and base-plan changes retain their current deferrals. A zero-price free period is an accepted tariff, not a Rating promotion engine. A credit trial is ordinary gross valuation plus Billing-owned allocation.

## Fact envelope and accepted terms

The following is a complete **semantic field contract**. Names are proposed SDK notation. A final owner schema must encode every row, conditional and refusal below; an opaque payload cannot replace these invariants. Every reference is tenant-qualified and resolves to immutable content with its version and digest. An omitted optional reference means “not applicable”, never “use the latest”.

| Field group | Required shape | Validation |
| --- | --- | --- |
| Protocol | `profile`, `schema_version`, `digest_version` | Supported explicit versions; an unknown required semantic field/version refuses the profile |
| Fact identity | `fact_id`, `fact_version`, `previous_fact_ref?`, `payload_digest`, `source_commercial_ref` | First version has no predecessor; successors name the preceding immutable version/digest. Same economic occurrence retains its ID. The producer allocates monotonic revisions transactionally |
| Group | `billing_group_id`, `subscription_id`, `seller_tenant_id`, `payer_tenant_id`, `currency`, `billing_window: [from,to)` | Immutable across versions of the same fact; changes need a separately authorized commercial operation, not an edit to this envelope |
| Attribution | `resource_tenant_id`, `line_id`, `component_id`, `item_id`, purchase/order references | All binding selections and lots belong to this commercial component and authorized tenant axes; caller identity never comes from these fields |
| Obligation | `kind: recurring / usage / one_time`, `obligation_state: active / zero`, `timing`, `billing_terms_ref` | `zero` explicitly cancels the economic obligation with lineage/reason; it is distinct from a live obligation priced at zero |
| Temporal evidence | For recurring/usage: `period`, complete timeline with chargeable slices, explicit nonchargeable intervals and `Unresolved` intervals; reasons/source refs and suspension-posture references | Half-open, ordered, non-overlapping intervals account for the declared extent with no implicit gaps. `Unresolved` is neither nonchargeable nor a zero tariff and blocks full valuation. Collection pause is deferred and has no representation in this profile |
| Slice | Chargeable: `[from,to)`, posture/policy refs, `allocations[]`; unresolved: interval, typed reason, authoritative evidence, affected lot/quantity/purchase provenance and retained known terms | Exactly one timeline segment at each declared instant. A chargeable slice contains all simultaneous lots; unresolved segments preserve known commercial facts without inventing accepted terms. Lots do not create overlapping temporal slices |
| Allocation | `lot_id`, exact textual `quantity`, `unit`, `accepted_terms_ref`, `purchase_action_ref` | A lot appears once per slice; compatible quantities sum to the component's committed quantity. One-lot and many-lot cases use the same schema |
| Accepted terms | Complete recoverable binding, plan/revision/item and selected dimension, price/model/money, stored currency/scale, SKU/version/descriptors, usage/proration/aggregation-policy refs, validity extent and acceptance/continuation provenance | A price ID alone is insufficient. Historical descriptors/policy must not be rebuilt from today's catalog. Subscriptions carries references/evidence, not calculated amounts |
| One-time evidence | `occurrence_id`, `qualifying_action_ref`, `applied_evidence_ref`, `applied_at`, `accepted_terms_ref`, `basis: Once / Units { quantity, unit }`; no recurring/usage window geometry | Accepted 2026-10-16: `Once` matches `flat`; `Units` matches `per_unit` with positive exact action-specific quantity and its agreed unit. Required applied evidence and frozen terms must agree. No implicit quantity of one or lookup of current subscription quantity. Occurrence identity is independent of price, transport attempt and removed phase IDs |
| Boundary/benefit evidence | Applicable cancellation cutoff/actual stop refs, trial episode/policy/grant refs and applied paid-transition ref | Keep actual runtime and commercial bound separate. No bonus balance, allocated money or assumed financial completion in a fact |

Fact timestamps use whole UTC seconds for compatibility with #5175 V60. Sub-second evidence is refused for this profile, never silently truncated; any broader precision requires a jointly versioned change. Quantity is an exact canonical decimal string, not binary floating point. Profile admission must respect the negotiated Rating numeric bounds even if a producer supports larger values.

For a zero-obligation replacement, retain the group/occurrence, prior fact reference, purchase provenance and an immutable reason/evidence reference. An empty slice set is allowed only in this explicit state. A genuinely zero-priced active obligation retains its slices, accepted zero binding and, for usage, its completeness evidence. Missing terms are neither kind of zero.

**Explicit unresolved successor accepted, 2026-10-16.** When an established obligation has a known boundary but no authorized continuation, Subscriptions publishes a full successor fact containing an explicit `Unresolved` interval and atomically publishes its exact successor seal (SUB-D-42). Preserve fact identity, period, known intervals, affected lot/quantity/purchase provenance, reason and authoritative boundary evidence; do not manufacture a binding for the unresolved interval. This is a complete description of commercial knowledge, not complete valuation evidence. Rating advances the authoritative fact head, invalidates stale work and keeps the full monetary replacement pending. Billing cannot use the older fact result to satisfy the new seal or accept a stale target after observing the newer commercial head. Existing posted effects and uncertain executions remain governed by their normal recovery/correction protocol; publication alone triggers no monetary reversal. Resolution publishes another full fact and successor seal, never mutates this version. A zero tariff and an evidenced nonchargeable interval remain distinct. This amendment does not waive new-sale, capture, activation or increase prerequisites, nor turn a mere unavailable read into proof of a new price end. Exact codec/type names and other SDK choices remain proposed.

**Digest proposal.** Each owner publishes a versioned canonical field list and golden byte vectors before enablement. The digest covers the protocol, identity, predecessor and all semantic fields above, including immutable reference digests; it excludes only the digest field itself and delivery metadata (event ID, retry time, trace ID). Use SHA-256 over that canonical representation. Normalize numeric text as in #5175; explicitly sort semantic sets by stable identity, reject duplicates, and retain ordered timelines. Distinguish absent, explicit null and empty where the schema does. Pin timestamp/UUID representation and domain separation per object/profile. Consumers verify the producer digest with that producer's codec; Rating's normalized `input_digest` is a different digest. No consumer hashes a reconstructed DTO using its current schema and calls it the producer's evidence.

## Binding authority and calculation evidence

The profile uses **accepted slices as the commercial authority**, while Pricing remains the price-selection owner. For each slice and lot, Rating obtains the exact accepted binding content and verifies its identity/digest, selection, currency/scale, model and permitted extent. Its calculation snapshot retains those immutable inputs, the fact and source-proof versions, and the evaluation generation. The fact's `accepted_terms_ref`, Pricing's binding digest and Rating's `calculation_snapshot_ref` are three distinct references.

**Mid-term continuation accepted, 2026-10-16.** At renewal or a known `ends_on`, Subscriptions obtains Pricing's permitted continuation under the accepted commercial policy and publishes the resulting frozen slice/lot mapping. Automatic adoption inside a running term requires an explicitly accepted continuation rule and satisfaction of its notice/assent prerequisites (SUB-D-41). A price closure or successful Pricing selection alone is not authority to change customer terms. A policy allowing changes only at renewal does not authorize a mid-term transition. Subscriptions never manufactures a rate or promises permanent prices. A late-discovered price end likewise requires an authoritative accepted continuation/correction and a successor fact before different terms can be used. Rating may request recovery or report unresolved coverage; it cannot turn an unrelated latest catalog answer into accepted commercial state. Missing authority, notice/assent or covered pricing leaves the affected full calculation pending: a known prefix is not a complete replacement and the unresolved tail is not zero. This chooses no automatic debt, free-service or shutdown policy. `effective_to` is not substituted for `ends_on`.

This explicitly replaces #5175's autonomous adoption of an `ends_on` successor **for this profile only**. A first-final freshness check validates the accepted timeline; it cannot adopt another price. First final and later input corrections consume authoritative accepted commercial evidence; a finalization delay proves no authority to reprice. Subscription-version reads may validate/recover an exact `source_commercial_ref`, but cannot independently change quantity/coverage under an unchanged fact version as T-D-82 currently proposes. A mismatch is pending/conflicting evidence, not a choice of whichever source arrived last.

**Proposed detection and SDK protocol; exact owner mappings remain open.** Pricing remains the selection owner, including its signup-selection fallback when a pinned binding no longer binds; a returned `new` price is not by itself either a refusal or customer authorization. Subscriptions must not reimplement that selection algorithm.

1. Use `PricesPublished` as a wake-up for an index of active/future accepted price dependencies, plus known-boundary scheduling and event-independent reconciliation. The event includes affected ended/predecessor prices, but its `effective_to` is not authoritative `ends_on`; recover the Pricing evidence. An ordinary informational window change alone does not authorize a new slice.
2. Read Pricing and stage the proposed continuation outside the Subscriptions mutation transaction. Recheck expected subscription/fact heads and continuation prerequisites at local application, including concurrent cancellation, increase and renewal. Commit the adopted timeline, full affected successor facts, exact successor seal, operation outcome and outbox atomically. Stale work recomputes against the current head; lost responses recover the recorded outcome.
3. Before a window's first final evaluation, Rating needs an authoritative observation adequate to validate its accepted boundaries. A discrepancy keeps the affected full result pending and requests Subscriptions reconciliation; an old complete result cannot be used to bypass a known unresolved discrepancy. Pricing unavailability supplies no positive evidence. Unchanged accepted content needs only retained validation evidence, not another commercial fact/seal. Scope and reuse observations by their proven coverage instead of assuming a call for every hourly child.
4. Candidate semantic exchanges are `report_terms_discrepancy { exact_fact_ref, slice_ref, pricing_observation_ref }` and `terms_reconciliation(exact_fact_ref) -> current(evidence_ref) | successor_published(exact_successor_ref) | pending(reason)`. Observation evidence binds the authorized Pricing query/date/pins or exact price read, answer content/digest and provider observation/snapshot semantics. A status response must not imply that a superseded requested fact is current. These are proposed operation roles, not adopted method names or deployed ports.

**Provider freshness gate.** Current `ResolvedBindings` carries no provider observation time/snapshot proof. The proposed first-final check requires an agreed authoritative committed-read guarantee, including concurrent publications and the clock/date semantics of Pricing's future-only explicit-end validation. A client receipt timestamp, TTL or finalization delay alone proves none of these. The daily observation reuse described in #5175 can be adopted only with those guarantees demonstrated; a date field by itself does not close the race. Historical replay uses recorded evidence, and a correction of usage under unchanged accepted terms does not select today's catalog or silently replace frozen descriptors. S-U08/S-U13 retain this provider/SDK and executed-conformance gate.

For example, a fact v1 accepted on October 1 uses A over `[October 1, November 1)`. On October 10, Pricing explicitly ends A on October 20 and selects B for continuation. With authorized policy and satisfied prerequisites, Subscriptions publishes full v2 with A over `[October 1, October 20)` and B over `[October 20, November 1)`, plus the exact successor seal. Without those prerequisites, Subscriptions publishes v2 with the known A interval and `Unresolved [October 20, November 1)`, plus its exact successor seal. Valuation remains pending; neither 19 days alone nor a zero tail is a complete October result. Authorized resolution then publishes v3 and its successor seal. Existing staged/posted Billing work follows the usual target fencing and correction protocol, never an additive second charge.

An administrative re-rate may select an authorized new evaluation generation and produce another full result against the same accepted terms. Changing commercial bindings requires the accepted commercial correction/continuation and successor fact. The request records both authorities if both change; a Rating operator's `rebind` flag alone cannot authorize new customer terms. Preserve old snapshots and generations for historical replay.

## Intake and replacement state transitions

Discovery by event and by pull enters the same durable intake path. Authenticate the producer/caller, authorize all tenant axes, validate profile/schema and producer digest, then recover exact references outside the local mutation transaction. Missing dependencies can be staged durably with pending reasons; they are not an accepted calculation input or proof of completeness.

| Incoming evidence | Local action | Financial meaning |
| --- | --- | --- |
| First valid fact, or a successor with validated chain | Atomically record immutable version, advance accepted fact head, invalidate affected work and queue scheduling/recovery | New work, not a charge or collection |
| Same identity/version/digest | Return/recover original intake disposition; no second work identity | Replay |
| Same identity/version with different digest | Retain conflict evidence and refuse advancement; compare retained historical versions too | No arbitrary winner or financial replacement |
| Older valid version | Retain/reuse history; do not regress head | No replacement of newer accepted work |
| Higher version with unavailable predecessor or input claimed as accepted | Stage and recover; expose pending dependency | No invented lineage or zero result |
| Valid successor explicitly declaring `Unresolved` with complete known lineage/evidence | Advance authoritative fact head, invalidate affected work and expose pending full valuation; await a resolving successor | Valid commercial publication and exact seal, no complete monetary replacement or fallback to an older fact |
| Explicit zero-obligation successor | Invalidate work, preserve historical children and publish a complete zero replacement once authoritative lineage is verified | Billing may correct prior effects; receipt is not refund proof |

For an accepted version, invalidate the prior child/manifest generation atomically with head advancement. Work prepared remotely or computed outside the transaction commits only if its expected fact head, input generation, manifest and relevant local source barriers still match. Otherwise discard/requeue the stale calculation; it cannot publish a new result for the old head. Old completed results remain readable as history, but status reads expose that they are superseded or awaiting replacement.

Persist each new result, its full immutable input cut, result head, receipt and publication/recovery entry in one transaction. Result revision increases across the stable fact family, including fact-version changes and re-rates. `delivery_id`/`run_id` identify delivery/calculation attempts or records; neither creates another economic obligation. A no-op retry returns the original receipt. No cross-gear transaction or remote call is held inside these local transactions.

## Valuation and completeness

**Recurring flat and proration accepted, 2026-10-16.** Preserve the full lot allocation and each purchase's accepted terms. Recurring supports Pricing's `flat` and `per_unit` models; graduated/volume/package models belong to usage, not recurring. A flat charge applies once per component obligation for its covered time under the same applicable flat terms, irrespective of seat quantity or number of simultaneous purchase lots (SUB-D-46). Distinct purchase/acceptance references do not by themselves make the tariff different. Do not prohibit multiple lots merely because the tariff is flat: quantities can still describe commercial rights. Multiple different simultaneous flat tariffs on one component remain unsupported without an explicit rule; neither sum them, select one nor reprice the old lot. Independently agreed component obligations remain distinct. Sequential authorized A-to-B continuation uses separate non-overlapping slices.

For recurring charges and the supported period minimum fee, the accepted proportional basis is the exact ratio of covered UTC seconds to the declared billing period's UTC seconds. Keep exact rational arithmetic through Rating; Billing alone rounds. This is the Subscriptions-side choice for R-30, not independent Pricing/Finance ratification or runtime readiness. Per-unit charges retain each lot's quantity, rate and covered interval. No generic FIFO/pro-rata distribution of pooled metered usage across differently priced lots is enabled.

**Pooled period minimum accepted, 2026-10-16.** For that profile, preserve T-D-38/T-D-78's per-price, per-subscription, per-billing-period and stored-currency/scale scope. Sum all eligible exact base charges in that scope before applying one minimum. Coverage is the **union** of its chargeable intervals, not the sum of overlapping lot durations. Compute `floor = minimum_fee × covered_UTC_seconds / period_UTC_seconds`, then `topup = max(0, floor − base_sum)`. Multiple lots, temporal slices, dimension values sharing that price or transport chunks do not each receive a floor. Different `price_id` values retain separate floors even when amounts are equal. This is tariff scope, distinct from Billing's invoice-line grouping.

If this scope spans facts, the aggregation/completeness/publication contract remains OPEN: this decision selects neither an admission ban nor a shared aggregation protocol. Independently flooring each fact, silently adding fact identity to the tariff scope, or suppressing the floor is invalid. The affected combination remains unenabled until that contract is agreed. Current Pricing code rejects minimum fees for `CalendarHour` or resource-scoped usage. This is an implementation gap for the newly required per-resource profile below, not a product prohibition. The pooled-period decision does not select its window/partial-window semantics or introduce a recurring tier model or recurring-period floor for one-time actions. R-30/R-34 owner adoption and executed conformance remain release gates, while the stated Subscriptions-side math is accepted.

**Per-resource minimum required — Jelastic use case, 2026-10-16.** The user identified a required case where the minimum applies separately to each resource. The pooled price/subscription/period rule above is therefore one profile, not the universal minimum scope. The new profile must preserve resource identity through the minimum calculation before any aggregation that would lose it; resources sharing a price must not implicitly share their minimum. Invoice-line layout and purchase lots do not determine this boundary.

**Individual and group scopes clarified, 2026-10-17.** Required examples are storage of container A, traffic of container B, and disk/storage pooled across containers in one node group. Distinguish **eligible consumption** (the agreed item/meter/charge kind) from **minimum target** (an individual resource or a resource group). A storage policy does not implicitly include traffic of the same container. The existing pooled profile remains available. A node group is not a BillingGroup, component, purchase lot or invoice-line grouping (SUB-D-47, SUB-D-48, SUB-D-49, SUB-D-50, SUB-D-51, SUB-D-52, SUB-D-53, SUB-D-54).

Proposed evidence contract, pending owner agreement: bind the accepted scope policy to stable individual/group identities and historical membership intervals from the authoritative owner, so replay does not consult only current membership. Creation, deletion, recreation and movement between groups require explicit lifecycle/partial-window rules; membership changes must not implicitly reset or duplicate a minimum. Missing required membership/usage evidence leaves the affected full valuation pending. Do not silently combine distinct prices, meters, currencies or payers; whether a group policy may cover multiple prices and how their eligible bases combine remain explicit contract questions, not an assumed single-price product restriction. Neither one fact nor one invoice line per resource/group follows from this requirement.

**Minimum scope is a tariff setting — accepted, 2026-10-17.** The user selected individual and group scope as alternative tariff settings. For the same eligible usage under the applicable accepted tariff, apply the selected scope once: separately for each resource, or once for the selected resource group. Do not stack individual floors and a residual group floor on that usage. Different usage kinds may have different settings. Preserve the chosen scope in the accepted terms for replay; invoice layout does not select it. Historical group membership and any ambiguity between candidate groups still require an explicit evidence/validation contract; scope selection does not authorize overlapping charges. The exact identity/evidence schema remains OPEN; the hourly rule and configurable partial billing-period treatment are recorded below. The window selection is recorded below; do not infer a resource generation/reset rule or UTC-time proration of this new minimum from the pooled profile.

**Monetary minimum accepted, 2026-10-17.** The user selected money as the minimum basis for the required individual/group usage profiles. Rating first evaluates eligible usage under its accepted tariff, then applies the monetary floor once to the selected target: `topup = max(0, applicable_minimum_amount - eligible_base_amount)` and `rated_amount = eligible_base_amount + topup`. The applicable minimum amount depends on the selected window: a partial hour retains the full hourly minimum as accepted below; partial billing-period treatment follows the accepted tariff setting described below. This does not increase metered or billable usage quantity or introduce a minimum-quantity tariff. Preserve exact base, minimum and top-up evidence in calculation provenance; Billing retains final rounding ownership. For a group target, aggregate eligible rated amounts of its members before applying the single floor. This closes the money-versus-quantity question without selecting cross-price aggregation or allocation of a nonlinear pooled tariff to individual targets.

**Minimum window selected by tariff — accepted, 2026-10-17.** Support both an hourly monetary minimum and a monetary minimum for the subscription billing period, selected in the accepted tariff. Evaluate the chosen floor independently for each selected target/window; choosing hourly evaluation does not imply hourly invoicing. Preserve the selected window and amount together in accepted terms and calculation evidence. This selects the two supported business window options, not simultaneous hourly and period floors or a new window codec. Calendar-hour alignment is selected below; timezone and exact SDK mapping remain owner-integration work; lifecycle boundaries and changes within a window remain OPEN. Partial billing-period treatment is configurable as recorded below.

**Full minimum for a partial hour — accepted, 2026-10-18.** When the selected target has an eligible chargeable interval in an hourly window, retain the full hourly monetary minimum even if that interval is shorter than an hour. Do not multiply the hourly minimum by the fraction of time covered. Apply the floor once to the selected target/window after eligible base valuation, not once per lot, slice, record or group member. For example, with a 1 EUR hourly minimum and 15 minutes of eligible service within one hourly window, a 0.70 EUR base produces a 0.30 EUR top-up and a 1 EUR total; a 1.20 EUR base produces no top-up. These are calculation examples, not tariff defaults. Full hourly minimum does not round metered usage or service duration up to an hour, waive inventory/attribution/coverage proof, or charge a window with no eligible obligation. Calendar-hour boundaries are selected below; timezone and lifecycle/identity rules still determine which windows/targets qualify. Recreation and group moves remain open. The separate billing-period setting below selects full or proportional minimum treatment for the new resource/group profiles; existing accepted pooled-period terms retain their original proration.

**Calendar-hour windows accepted, 2026-10-18.** The user selected clock-aligned hourly windows, not successive 60-minute windows starting at resource activation. For an unchanged applicable tariff and target, eligible service from 10:50 to 11:10 intersects two windows, 10:00–11:00 and 11:00–12:00; each receives the full hourly minimum, evaluated against that window's own eligible base. Excess above the minimum in one hour does not satisfy another hour's minimum. Use half-open interval boundaries for attribution: service ending exactly at 11:00 contributes no interval to the next hour; service starting at 11:00 belongs to that next hour. Calculate a minimum once per target/window regardless of record or slice count. Calendar-hour alignment does not itself choose a timezone: exact mapping to Pricing's timezone/window contract remains open. Group membership, tariff changes and lifecycle identity remain separate open contracts. Partial billing-period treatment follows the tariff setting below. These examples are specification cases, not executed runtime tests.

**Configurable partial billing-period minimum — accepted, 2026-10-18.** For the new individual/resource-group billing-period profiles, the tariff explicitly selects full minimum or proportional-to-time minimum for a partial eligible period. Preserve that choice with the minimum amount, scope and window in immutable accepted terms; replay uses those terms. In full mode, any qualifying partial period retains the full period minimum once per selected target/window. In proportional mode, reduce the minimum by the eligible duration divided by the full billing-period duration, then compare it with the eligible rated base. For a 30 EUR minimum over a 30-day period with 10 eligible days, the applicable floor is 30 EUR in full mode or 10 EUR in proportional mode; a base above the applicable floor is unchanged. These are examples, not fixed month lengths or tariff defaults.

The accepted choice is the two business modes. Exact SDK names/defaulting, time precision and authoritative eligible-duration evidence (especially for changing group membership) still require owner mapping; do not multiply group coverage by member count. A missing setting must not silently choose new commercial terms. Existing accepted pooled-period proration is preserved. The full minimum for a partial calendar hour also remains unchanged; this decision makes partial billing-period treatment configurable, not hourly proration. Lifecycle, cross-price and tariff-change questions remain open.

Current Pricing [`usage_policy::refuses_minimum_fee`](../../../pricing/pricing/src/domain/usage_policy.rs) rejects both resource scope and hourly windows, with the same restriction in commercial admission. [Pricing PC-P07](pricing-proposal.md#required-changes) must define the appropriate versioned policy/read/acceptance/validation changes; removing the guard alone is insufficient. Rating needs resource-scoped calculation and provenance plus authoritative resource/ownership/coverage evidence, including resources with zero usage. Resource inventory alone does not establish zero consumption: absent usage records still require the agreed coverage/completeness proof before a zero base can be rated. A monetary resource floor must also define its eligible base when usage tariff aggregation is pooled or nonlinear; separate scope fields alone do not make that combination meaningful. Subscriptions supplies the agreed commercial and attribution/recovery evidence rather than calculated amounts. Exact schema, completeness, lifecycle/correction and aggregation contracts remain OPEN; the requirement does not by itself create one commercial fact or invoice line per resource. Existing pooled terms retain their original interpretation.

**One-time.** One qualifying action schedules one non-periodic valuation unit. **Calculation basis accepted, 2026-10-16:** `Once` means one agreed flat charge for that action, never multiplied by seats; `Units { quantity, unit }` carries the positive exact quantity frozen for the qualifying action under a per-unit tariff (SUB-D-43). Rating validates basis, model, unit and applied evidence against the accepted terms; missing quantity, incompatible unit or model/basis mismatch is invalid, never an implicit one or the current component quantity. A later subscription increase changes neither the original occurrence nor its quantity. Additional separately agreed chargeable work gets its own occurrence; an authorized correction of the original action replaces its existing fact and exact seal while preserving occurrence identity. Exact codec/field names remain owner-integration work. Its frozen terms determine the fee; an allocation, reservation, advance, resume, conversion or technical attempt alone schedules nothing. A correction uses the same occurrence and can explicitly zero it. Any minimum fee follows the one-time accepted tariff's declared scope; a standalone occurrence must not accidentally accrue a month's recurring fee. No catalog-copy bypass around Rating is allowed.

**Usage.** A published usage parent and its accepted policy establish expected windows independently of arriving records. Rating enumerates every required window, including empty and partial boundary windows, before asserting completeness. Partial-hour data needs an explicitly supported interval attribution/fold rule; a scalar hourly peak cannot be split proportionally by assumption. A discovered unsupported intra-hour boundary stays pending/refused under the profile rather than allocating guessed usage.

Each usage manifest includes `manifest_ref` (identity/revision/digest/predecessor), exact fact reference, policy reference, scope/window geometry, full expected child membership, selected child result references, and independent inventory/attribution/coverage/record-set barriers. Coverage must match the exact resources, meter versions, intervals and stored record digest; no elapsed delay or absence of records substitutes for it. `billing_group_kind=published` and `evidence_mode=full` are required. A delay may postpone finalization but never waive evidence. Accepted source loss is an explicit repair/exception outcome, not normal full evidence or a fabricated zero.

A manifest change retains the old membership. Removed previously delivered children are accounted for by explicit replacement/zero lineage; they are not erased from history. A parent monetary delivery contains the full current result of all its required children. Child reads are diagnostic and recovery inputs, never additional Billing deliveries. For a fully zeroed obligation, the authoritative zero successor accounts for prior child membership without waiting for unrelated future usage coverage; this is commercial removal, not a claim of measured zero usage.

Commercial membership, ownership scope, usage closure and rated completeness are separate proofs. Rating may finish a fact before Billing has its complete commercial seal. Billing may not accept the group target until it has both compatible commercial membership and all required rated evidence. Unknown Billing invoice state never blocks Rating's tariff math.

**Seal matching accepted, 2026-10-16.** A commercial seal names the full exact `(fact_id, fact_version, payload_digest)` set (SUB-D-40). Billing compares the selected result's source reference for equality, not a minimum-version test. A result for fact v5 cannot satisfy a seal entry for v4; it waits for the successor seal. A later complete calculation result for the same fact v4/digest can replace the previous result under that seal, without a new Subscriptions seal, subject to current commercial-head, result/manifest freshness and financial-execution guards. Billing freezes the new result refs in its successor financial target. This accepts only the seal-version rule; other proposed SDK and cross-owner decisions remain open.

## Canonical result and Billing handoff

Extend/adapt the existing full `BillableItemDeliveryV1` contract with the following required semantics under the agreed version. Keep its exact major-unit amount representation and complete-parent delivery behavior.

| Result field group | Required contents and rule |
| --- | --- |
| Envelope | Adopted profile/schema/digest versions, stable fact/result family, `result_revision`, preceding result reference, `result_digest`, `delivery_id`, immutable group/tenant axes |
| Input cut | Exact source fact ID/version/digest, accepted slice/lot/binding references, source commercial revision, calculation/input digest, engine generation(s), calculation snapshot references |
| Completeness | `complete=true`, `zero_result`, `evidence_mode=full`, manifest reference/digest for usage; no pending result serialized as a complete delivery |
| Lines | Stable `line_key`, Billing-owned/versioned `invoice_line_key` and its full reconstructible components, item/kind, exact amount and stored scale, immutable invoice descriptors, full contribution provenance |
| Provenance | Fact, slice, lot/purchase, binding, SKU/version, price/entry, window/result and exact contribution references; enough to attribute original service and customer/platform/benefit boundaries |
| Floor details | Top-up contribution with its price/scale, aggregation-scope identity, coverage union, calculation evidence and owning line; detail entries are explanatory references to money already included in lines, not additional billable amounts |
| Empty versus zero-valued | A complete empty replacement has `lines=[]` and exact source/occurrence, reason/evidence and replacement lineage. An active obligation valued at zero retains zero-valued lines, classification, accepted terms and calculation evidence. Missing conditions/data produce pending status, not either monetary form |

**Empty replacement, zero-valued lines and pending accepted, 2026-10-16.** These have distinct meanings (SUB-D-45):

- A complete replacement with `lines=[]` states that the fact now contributes no monetary lines. Under the selected exact seal and normal target/execution guards, Billing removes that fact's prior contributions while preserving other facts' contributions and all history. A fully withdrawn obligation uses this form, with the reason and evidence recoverable from its source. Empty lines alone are not a cancellation reason, invoice deletion or proof of a completed refund.
- An active obligation evaluated at zero retains its zero-valued lines, invoice classification, frozen accepted terms and calculation provenance. A zero tariff or proven zero usage does not remove the commercial obligation. Usage still needs its required completeness evidence; zero usage yields zero money only if the full accepted tariff, including any applicable minimum fee, evaluates to zero. Billing owns invoice presentation and may decide how to display these lines without discarding their underlying evidence.
- Missing conditions or data yield structured pending status and no complete monetary delivery. A known prefix, timeout or absent evidence cannot be encoded as empty lines or zero-valued lines.

A zero total is not permission to collapse classified/provenanced lines into an empty result. Delivery remains a complete replacement; omission of an old line removes that fact's old contribution under the normal replacement protocol. The exact mapping of the existing `zero_result` flag belongs to the versioned SDK codec: it must preserve this distinction and validate consistency with the payload, never imply withdrawal or financial completion by itself. This semantic decision does not by itself approve a changed meaning for a shipped V1 field.

Every amount is `{numerator, denominator, currency, currency_scale}` in exact major units, with reduced canonical strings and a positive denominator. Zero is `0/1`; `currency_scale` is an integer. Preserve #5175's published bounds and reject overflow/inexact conversion; schema goldens and negotiated producer limits must agree before admission. A result can have different stored scales on separate lines; cross-scale addition is forbidden. Rating carries no monetary rounding mode and never applies Billing rounding. Quantity business rounding, where declared by the accepted model, remains recorded separately.

The pinned #5175 proposal bounds are `abs(numerator) < 10^84`, `0 < denominator < 10^64`, and quantities with at most 60 integer and 28 fractional digits. These remain proposed cross-owner limits under R-33, not a claim that every Pricing/Billing operation accepts the whole range. Each adopted engine generation freezes its bounds. Billing separately publishes posting/aggregate limits; out-of-range values cannot wrap, saturate or become zero.

`result_digest` binds the entire delivery's semantic content and input cut, not merely child membership. An adopted mapping may reuse `manifest_digest` only if its canonical contract covers all those fields; otherwise keep both explicit. An equal old revision/different digest is still a conflict if that version is retained, even after the head advances. Full replacements can skip materialization of intermediate calculation revisions after immutable lineage is recovered; **they cannot skip recovery of a financial operation whose outcome is unknown**. Retain the immediate predecessor relation on every produced revision.

Billing replaces the selected contribution set for this fact; it does not add the new full amount to the old one. A vanished line key in a complete replacement removes that fact's prior contribution while preserving its history. Billing sums compatible exact contributions by its adopted invoice-line key, including top-ups, and rounds once HALF_EVEN at the stored scale. It derives corrections from the rounded new aggregate and actual cumulative posted history. It validates aggregate posting bounds across facts, beyond Rating's per-fact bound.

The proposed invoice equivalence tuple retains #5175's `billing_group_id`, subscription sub-line, meter/item identity, dimension key/value, `invoice_line_kind`, currency, stored scale, unit, GL code, tax category and invoice template. Its codec/version and final field types belong to Billing's R-32 adoption. Fact/result revision, hour, `price_id` and `lot_id` do not independently split this tuple; they remain contribution provenance. A changed classification or scale can move a contribution to another key in a full replacement, requiring Billing to update both old and new aggregates. A top-up of one rated line shares that line's invoice key. A floor spanning several invoice keys needs Billing's explicit allocation/posting rule: the exact floor alone does not prove that separately rounded lines reach it (5.005 + 5.005 + 19.99 can post 29.99 against a floor of 30). That combination remains gated under R-32; Rating cannot fix it by rounding an amount.

For multiple contributing facts, Billing must store an immutable aggregate-evidence object naming the exact source refs/digests and financial target. Ledger's optional single snapshot field may reference that recoverable aggregate under an agreed adapter mapping. It must not pick one fact and discard the others, or split one invoice-line equivalence class into separately rounded postings merely to fit the field. If the financial adapter cannot preserve that mapping, the target remains pending. This is the proposed closure of R-26, not a claim that Ledger already implements aggregate evidence.

RB04 governs invoice-version fencing and serialized financial execution. Target acceptance atomically records exact references, expected invoice basis, stable execution key and outbox. Remote execution uses that key, and an unknown predecessor is recovered/fenced before successor effects. Advances and grants change Billing's allocations, never Rating's gross tariff or economic occurrence. Billing status reads distinguish target staged, target accepted, work pending and effect applied/replayed; Rating's delivery receipt proves none of the latter financial outcomes.

Operations below describe required capabilities, not newly claimed SDK methods or REST routes. Reuse existing proposed interfaces where semantics fit; add versioned exact-reference reads where the current `find_runs/get_run/window_results/deliveries_since` surface is insufficient. SDK calls take `SecurityContext`; REST adapters use canonical errors and RFC-9457 Problems. Batching and page limits belong to the negotiated operating profile, not tariff policy.

| Rating: work/head status | Fact ID plus optional required exact fact reference | Exact evaluated/staged fact reference, accepted head, state, recoverable work identity, structured blockers and optional latest complete result with its own exact source reference. Data/terms-pending requires a nonempty blocker list. An older complete result cannot masquerade as completion of the requested/current fact |
| Rating: result snapshot and catch-up | Authorized group/range or checkpoint vector | Complete selected result heads at fixed barriers, exact manifests and subsequent commit-ordered result changes, including explicit zero replacements |

Use the Subscriptions [recovery implementation profile](../features/09-consumer-contracts.md#38-recover-gaps-cursor-loss-and-retained-history) for both commercial input discovery and the required Rating output guarantees: transactionally committed partition journal, immutable snapshot descriptor, historical head reconstruction, stable keyset pages, explicit terminal page, and catch-up strictly beyond the snapshot barriers. Positions from unrelated streams/partitions are never compared as a global clock. Concurrent cross-partition references must still form the compatible immutable seal/result cut; a vector alone proves no distributed transaction.

**Difference from #5175:** its delivery `feed_seq` is a per-partition outbox claim sequence and explicitly need not follow commit order. It remains useful for delivery but is not by itself the committed completeness barrier required here. Rating must either add a commit-ordered recovery journal with the result transaction or specify and prove an equivalent no-late-lower-position protocol. Never relabel that claim sequence as a commercial barrier. Keep delivery acknowledgement/claim/checkpoint identities separate.

Each page carries a snapshot/stream identity, declared scope/query/profile, covered source interval, fixed upper barrier(s), immutable record refs, continuation and an explicit complete flag. For filtered reads, distinguish a covered interval with no matching entries from missing sequence history. A continuation is opaque and integrity-protected; reauthorize every page and reference. A changed/expanded scope requires a fresh bootstrap. No service account bypasses PDP, and inaccessible history is not disclosed by errors or retention bounds.

Consumers may acknowledge durable staging, but advance their **applied** checkpoint only with validated local projection/inbox state in the same transaction. Missing references or gaps hold that checkpoint; downstream invoice execution has its own cursor/state. Install a bootstrap generation only after all pages and cross-references validate, retaining the previous installed generation while incomplete. Snapshot expiry with intact history requests rebootstrap; actual history loss requires authoritative historical repair or an explicit repair-required exception. Current active lists cannot recover deleted/zero obligations or old financial work.

Retention must cover the enabled correction/finalization/outage profile and keep financially referenced versions, engine snapshots, grants and execution lineage recoverable through their required lifetime. Publish concrete limits before enablement. Do not copy the PR's broker-retention duration as a guarantee of historical recovery.

## Errors and capability negotiation

**Structured pending reasons accepted, 2026-10-16.** A successful Rating work/status read for a fact waiting on conditions or data MUST expose a nonempty `blockers` list, bound to that exact `(fact_id, fact_version, payload_digest)` (SUB-D-44). Several blockers can coexist; a single generic pending label is insufficient. The semantic shape below is required; exact SDK names/codecs remain owner mapping work.

| Status content | Required meaning |
| --- | --- |
| Exact fact reference, accepted head and state | Identify which version the status describes; a staged requested version must not be confused with the accepted head |
| `blockers[].code` | Stable machine-readable reason such as `continuation_pending`, `accepted_terms_unavailable`, `usage_coverage_missing` or `predecessor_missing`; display text is supplementary |
| `blockers[].affected` | The affected interval, lot, child window or exact missing dependency; explicitly use fact-wide scope when applicable |
| `blockers[].source` | The responsible dependency/owner, such as Subscriptions, Pricing, the usage/coverage provider or Rating recovery; this is not a claim of remote work completion |
| `blockers[].evidence_ref` / dependency reference | Recoverable origin of the finding. For source `Unresolved`, reference its exact fact and segment/reason evidence. For missing data or unavailable providers, identify the missing dependency and retained local observation; never invent evidence of a remote outcome |
| `blockers[].resolution` | The expected resolution route: successor fact, exact-object recovery, coverage confirmation or provider reread; a route is not an authorization or a promise that retry will succeed |
| Optional latest complete result reference and its exact source fact reference | Historical/recovery evidence, explicitly distinguishable from completion of the current/requested version |

Subscriptions owns the reason and evidence embedded in its `Unresolved` segment. Rating retains that source link in its status instead of inventing independent commercial authority. Rating durably records its own findings, including missing usage coverage or predecessor recovery, so they remain inspectable after restart. Resolving one blocker does not hide the others or assert a complete result; subsequent status reflects validated resolution for the appropriate fact/work generation. Status does not require a monetary delivery, and no pending payload is sent as a complete result. Reads remain scoped and authorized, including evidence references. This accepts structured pending reasons; the separately accepted empty/zero-valued result semantics are defined above. Neither decision establishes a delivered SDK/provider contract.

These are proposed **semantic reason names**, to be mapped by each owner to its canonical SDK error/status vocabulary. They do not add an ad hoc HTTP API. A successful status read may report durable pending work; that is different from a failed read or a rejected command.

| Condition / reason | Disposition | Recovery |
| --- | --- | --- |
| Unsupported profile/schema, `capability_unsupported` | Refuse affected profile before fee-bearing effects | Negotiate a supported combination; no fallback to one lot, derived groups or delay-only |
| `fact_invalid`, `instant_not_whole_second`, `quantity_out_of_range` | Reject/quarantine invalid version without head advancement | Correct producer evidence under valid revision semantics; never truncate |
| `identity_conflict`, `digest_conflict`, incompatible tenant/group | Conflict; preserve existing head | Recover authoritative owner lineage; a retry key does not resolve it |
| `predecessor_missing`, `accepted_terms_unavailable`, `continuation_pending` | Durable pending, no complete monetary delivery | Fetch exact history/accepted continuation; retry same work identity |
| `binding_mismatch`, `binding_currency_mismatch`, `price_uncovered` | Block affected valuation with source references | Authoritative correction or supported commercial continuation; never latest-price/zero fallback |
| `allocation_unsupported`, `boundary_split_required` | Refuse unsupported profile before new commercial effects; keep discovered historical work unresolved | Jointly specified usage/floor/boundary policy, not guessed allocation |
| `scope_missing`, `coverage_missing`, `coverage_mismatch`, attribution gap/ambiguity | Pending completeness | Recover independent proofs and invalidate affected generations |

If capability disappears after an obligation was accepted, retain and expose the blocked obligation for recovery/remedy rather than losing it or substituting a cheaper/zero profile.

## Examples

**Accepted flat/floor examples (illustrative 30-day period).** With no other tariff charges, two simultaneous lots under the same flat EUR 30 terms for the whole period produce EUR 30, not EUR 60. An authorized sequential transition from flat EUR 30 for 15 days to EUR 60 for 15 days produces exact EUR 45. For one per-unit price, a full-period lot contributes EUR 20 and a later lot contributes an already-prorated EUR 3; with minimum EUR 30 and full-period union coverage, base EUR 23 receives one EUR 7 top-up. If all lots under that price cover only the final 15 days, its floor is EUR 15, not EUR 30. Different prices A/B with minimums EUR 30/EUR 40 covering successive halves have separate floors EUR 15/EUR 20, each compared with its own base charges. None of these amounts is a product default.

**Concurrent purchases.** Ten units use the accepted EUR 2 monthly tariff. Two added units use a later EUR 3 tariff. A full-month example totals EUR 26; an increase part-way through a month uses the accepted served intervals and proration. Rating must never reprice all twelve units at EUR 3. Replaying the purchase adds no second lot.

With covered-UTC-seconds proration, no floor and an October 16 00:00 UTC increase in `[October 1, November 1)`, A contributes EUR 20 and B contributes `6 × 16/31`; the exact full replacement is `716/31` EUR, posted as EUR 23.10 if one invoice-line key applies. The predecessor was EUR 20; Rating sends `716/31`, not a `96/31` delta. The source contains one A-only slice followed by one A+B slice.

**Shared floor.** Two simultaneous lots at the same price/scale contribute EUR 10 each for the full period with a EUR 30 floor. Their coverage union is one period: ordinary charges total 20, top-up 10, full result 30. Two genuinely distinct prices with their own EUR 30 floors produce 60. If the same shared price scope spans two facts, per-fact top-ups are not enabled until a common aggregation owner/barrier is agreed; invoice transport cannot decide the tariff scope.

**One-time charge.** An accepted EUR 50 setup action completes. Rating emits the full EUR 50 result once for its stable occurrence. Billing applies an existing EUR 50 advance, if applicable, without collecting twice. A resumed subscription or rebuilt technical attempt creates no new setup occurrence.

**Exact rounding.** Two exact contributions of EUR 0.005 to the same invoice line stay exact in Rating and sum to EUR 0.01 for Billing. If they belong to two distinct invoice-line keys, each rounds to EUR 0 under HALF_EVEN. Grouping is contractual; it cannot be changed by transport convenience.

**Correction after posting.** An exact EUR 0.006 line was posted as EUR 0.01. Rating replaces it with exact EUR 0.005. Billing rounds the corrected total to EUR 0, then issues a EUR 0.01 credit note. Rating does not round a negative difference or post an invoice adjustment.

**Credit-trial correction.** Normal rated value changes from EUR 30 to EUR 25 under the same eligible EUR 100 grant. Rating publishes a full replacement of EUR 25. Billing restores EUR 5 once if still eligible; after original expiry, history changes but spend permission remains zero.

## Shared contract adoption checks

The older local slices contain `periodState` prerequisites and independent `Adjustment` dedup rows that conflict with this proposed profile. They remain baseline evidence in this PR; do not copy them into the newer design during adoption.

- Preserve the current #5175 rule: Billing period state is an observation only. Complete frozen commercial/usage inputs can be valued and a full result can be persisted/published while the Billing projection is absent. Never substitute an unknown period state with `open` or `closed_posted`.
- Apply that rule consistently to evaluation-context assembly, unit synthesis, correction routing and delivery. In the old layout those are foundation 01, corrections 08, consumer contract 11, synthesis 14 and handoff 16; use the equivalent contracts/features in the current consolidated design.
- Deduplicate the RB monetary lane by stable full-result identity, revision and digest. A replay is a no-op, lower versions cannot replace the accepted head, and equal revision with different digest conflicts. Legacy `Adjustment` keys in old contracts 11 and 15 are not a second RB financial lane.
- Billing recovers its authoritative invoice revision and predecessor financial outcomes before applying the new target. Rating publication does not imply invoice execution, and missing Billing history keeps financial work pending.

**Example.** The full frozen inputs yield EUR 25 while the Billing period-state projection is unavailable. Rating still publishes the full EUR 25 result. Billing stages it and recovers whether EUR 30 was already posted before choosing a draft replacement or an idempotent EUR 5 credit. The missing projection neither blocks tariff math nor authorizes an assumed financial correction.
